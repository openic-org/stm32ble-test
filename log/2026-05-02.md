# Session Log — 2026-05-02

## What was done

### Phase 3 (continued) — Fix PHY update failure and diagnose throughput ceiling

#### Problem: throughput stuck at ~32 KB/s despite 2M PHY, DLE, and 7.5 ms configured

Serial output showed `PHY CMD FAILED: 0x07` (Memory Capacity Exceeded). Root cause: the server
was calling `hci_le_set_phy()` while DLE negotiation was still in progress. The BLE LL only
allows one LL Control Procedure at a time; calling a second one returns 0x07.

The two DLE events observed on connect:
```
DLE UPDATE: MaxTxOctets=251 MaxRxOctets=27    ← asymmetric (server's view)
DLE UPDATE: MaxTxOctets=251 MaxRxOctets=251   ← both sides complete
```
PHY must only be requested on the second event (when both octets reach 251), not at the start of
`LinkConfiguration()`.

#### Fix: sequential DLE → PHY → connection interval pipeline

Restructured the on-connect sequence in `server/STM32_BLE/App/app_ble.c`:

1. **`LinkConfiguration()`** — issues DLE only (`hci_le_set_data_length(251, 2120)`)
2. **`HCI_LE_DATA_LENGTH_CHANGE_SUBEVT_CODE` handler** — waits for `MaxTxOctets=251 AND MaxRxOctets=251`, then calls `hci_le_set_phy(2M)`
3. **`HCI_LE_PHY_UPDATE_COMPLETE_SUBEVT_CODE` handler** — schedules connection interval update (`CFG_TASK_CONN_INTERV_UPDATE_ID`)
4. **`HCI_LE_CONNECTION_UPDATE_COMPLETE_SUBEVT_CODE` handler** — logs actual interval

Same DLE handler added to `client/STM32_BLE/App/app_ble.c` for visibility; client does not
initiate PHY update (server drives it).

#### Result after fix

```
DLE CMD OK
DLE UPDATE: MaxTxOctets=251 MaxRxOctets=27
DLE UPDATE: MaxTxOctets=251 MaxRxOctets=251
PHY CMD OK, waiting...
PHY UPDATE OK: TX=2 RX=2
CONN UPDATE: interval=7.50 ms
DataThroughput = 132090 bytes/s
```

Throughput: **~133 KB/s unidirectional, ~63 KB/s bidirectional**.

### Mblock pool analysis and tuning attempts

#### Why bidirectional is half of unidirectional

In unidirectional operation (server TX only), each connection event at 2M PHY / 7.5 ms contains
~4 server notifications. In bidirectional (both sides sending), each event holds ~2 notifications
AND ~2 client writes, because each exchange uses two full 251-byte PDUs (one each direction):

| Mode | PDU exchanges/event | Server throughput | Client throughput |
|---|---|---|---|
| Unidirectional | 4 (client empty ACK + server notify) | ~133 KB/s | 0 |
| Bidirectional | 2 (client write + server notify) | ~65 KB/s | ~65 KB/s |

#### Attempt 1: reduce `CFG_NUM_RADIO_TASKS` from 2 to 1

Theory: `BLE_STACK_MBLOCKS_CALC(247, n_link=1, 0) = 20` (vs 30 for n_link=2). With total mblocks
fixed at 62, shifting minimum from 30 to 20 frees 10 more mblocks for TX queuing.

Outcome: **boards stopped connecting**. With `NumOfRadioTasks=1`, the BLE controller can only
schedule 1 simultaneous radio event. The connection establishment transition (advertising → 
connection handshake) appears to require ≥2 concurrent radio slots. Reverted.

#### Attempt 2: reduce `CFG_BLE_ISR1_FIFO_SIZE` to free RAM for 4 more mblocks

`ISR1_FIFO_SIZE` (768 bytes) is for non-critical ISR events (scan reports, IQ samples). The
server never scans and the client scans only briefly. Reducing from 768 → 512 frees 256 bytes —
enough to raise `CFG_BLE_MBLOCK_COUNT_MARGIN` from 32 → 36, giving 66 total mblocks.

Mblock math with 66 total, n_link=2 (min=30):
- RX minimum: `(8+2) × 2 + 1 = 21` mblocks
- TX capacity: `floor((66−21)/9) = 5` notifications queueable
- Predicted: 5/event × 244 B / 7.5 ms = **163 KB/s unidirectional**

Outcome: **~135 KB/s unidirectional, ~65 KB/s bidirectional** — essentially no change.

---

### Root cause: air-time ceiling, not buffer size

At 2M PHY, each server→client exchange costs:
```
client empty ACK: 44 µs
T_IFS:           150 µs
server notify:  1048 µs  (262-byte on-air PDU at 2 Mb/s)
T_IFS:           150 µs
= 1392 µs/exchange
```

Per-event overhead (radio warmup + guard time before next anchor): ~700 µs.

```
Available: 7500 − 700 = 6800 µs
6800 / 1392 = 4.88 → 4 exchanges/event
```

5 exchanges = 6960 µs, which fits in 7500 µs in theory, but not reliably given the guard time.
The stack can occasionally squeeze in 5 (explaining the ~135 vs ~133 KB/s variance), but the
typical steady-state is 4/event. Queuing more mblocks has no effect once 4 are already the
air-time limit.

## Final throughput results

Hardware: NUCLEO-WB09KE (server) ↔ custom STM32WB09TE (client)
Firmware: 2M PHY, DLE=251, ATT MTU=247, connection interval=7.5ms, no bonding, no LPM

| Mode | Measured | Theoretical ceiling |
|---|---|---|
| Unidirectional (server → client) | **~135 KB/s** | 163 KB/s (5×244B/7.5ms) |
| Bidirectional (both sending) | **~65 KB/s** each direction | 65 KB/s (2×244B/7.5ms) |

Efficiency (unidirectional): 135/163 = 83% of gross theoretical maximum. The ~18% gap is
consumed by per-event radio overhead (~700 µs of the 7.5ms window). This is the practical
ceiling for standard BLE GATT notifications on this hardware.

## Paths to higher throughput (not pursued)

- **L2CAP CoC** — reduces per-PDU header overhead slightly; marginal gain
- **ST proprietary radio** — `USE_RADIO_PROPRIETARY_DRIVER=1` bypasses BLE, uses raw action
  packets; could reach ~250 KB/s but breaks BLE interoperability
- **Multiple simultaneous connections** — requires a hub topology, not applicable here
